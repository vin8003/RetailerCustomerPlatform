# OE-313 F follow-on — top-level `unit` on sales-return line items

Work snapshot. Durable: [sales-return-item-unit.md](../requirements/sales-return-item-unit.md).

List/detail serializers already expose `Product.unit`. Purchase invoice lines echo it (OE-310). Sales-return line items omitted it. CTO overnight lock is this EXTEND only: echo the same top-level `unit` on `SalesReturnItemSerializer`.

## Gap list (scout)

| AC | Before this slice | After |
|----|-------------------|--------|
| Sales-return item includes `unit` | List/detail / PI items only | **EXTEND** — same model value |
| Null/empty `unit` stays null/empty | List/detail pass through | same on sales-return items (no invented `piece`) |
| Auth/tenancy | Shop-scoped sales returns | unchanged |
| Unit conversion / write APIs | Missing | still out of scope |

## Done in this change (EXTEND, one slice)

- `SalesReturnItemSerializer` exposes `unit` from `product.unit` (read-only)
- List queryset prefetches items with `select_related('product')` so the echo does not add a product query
- Matches list/detail for the same SKU
- Tests: parity with list/detail, empty passthrough, write ignore, auth, tenancy, pack identity without conversion, no extra product query when product is already select_related

Out of scope: unit-conversion engines, pack write, inventory.adjust, ProductSearchSerializer Meta, POS views, customers/*, orders serializers, purchase invoice serializers, timeline/OFD/khata/UPI/slots, FE, merge, Jira Done, live `*.ordereasy.win`.
